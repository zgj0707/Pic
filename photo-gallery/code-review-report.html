📋 项目概览

Pic 是一款面向独立摄影师的样片库管理桌面应用，基于 Electron 构建，提供照片导入、EXIF 管理、标签评分、批量重命名、素材浏览器等功能。

整体评价

Pic 作为一款垂直领域的工具型应用，功能覆盖面完整——从照片导入、EXIF 读写、标签评分、批量操作到素材浏览器，基本满足摄影师样片管理的核心需求。但项目存在架构层面的结构性问题：前端 2983 行代码堆积在单个 HTML 文件中无任何模块化、多处安全配置存在高危风险、数据库写入策略导致性能瓶颈、存在约 500 行死代码。这些问题在当前数据量较小时不会暴露，但随着照片库增长到数千张，会逐步成为可用性和可维护性的障碍。

架构关键问题：
  • Preload 直接暴露了 db:query / db:get / db:run 三个通用 SQL 接口，渲染进程可执行任意 SQL（包括 DROP TABLE）

  • metadata.ts 完整实现但从未被 main.ts 注册调用，属于纯死代码

🔴 严重问题 (Critical)

这些问题涉及安全漏洞或会导致功能异常，建议立即修复。

Critical C1. webview 安全配置完全禁用同源策略
public/index.html:598-602

素材浏览器的 webview 同时设置了 webpreferences="...webSecurity=no..." 和 disablewebsecurity，完全禁用了浏览器的同源策略。这意味着 webview 中加载的任何网页（包括被 XSS 注入的页面）可以发起任意跨域请求、读取任意来源的响应数据，甚至访问本地 file:// 资源。

<webview src="https://www.xiaohongshu.com"
  webpreferences="...webSecurity=no;..."
  disablewebsecurity
  allowpopups></webview>
修复建议：移除 disablewebsecurity 和 webSecurity=no。如果需要绕过 CORS 限制，使用 session.webRequest.onHeadersReceived 精细化修改响应头，或使用代理服务器转发请求。
Critical C2. 主窗口 webSecurity 关闭 + 通用 SQL 接口暴露
electron/main.ts:36 | electron/preload.ts:9-11 | electron/services/database.ts:168-183

三个独立的安全问题叠加形成高危链路：

(1) 主窗口 webSecurity: false 禁用了主窗口的 Web 安全策略。

(2) Preload 通过 contextBridge 直接暴露了 db:query、db:get、db:run 三个通用 SQL 执行接口，渲染进程可以执行任意 SQL 语句（包括 DROP TABLE、DELETE FROM photos 等破坏性操作）。

(3) dbAdapter.get() 和 dbAdapter.query() 内部使用 substituteParams() 函数进行字符串拼接 SQL，而非使用 prepared statement 参数绑定。虽然对单引号做了转义 (replace(/'/g, "''"))，但这种方式本质上是脆弱的字符串拼接，存在 SQL 注入风险。

// database.ts - 字符串拼接 SQL (不安全)
function substituteParams(sql, params) {
  return sql.replace(/\?/g, () => {
    const param = params[paramIndex++];
    if (typeof param === 'string')
      return `'${param.replace(/'/g, "''")}'`; // 仅转义单引号
    return String(param);
  });
}
// preload.ts - 暴露通用 SQL
database: {
  query: (sql, params) => ipcRenderer.invoke('db:query', sql, params),
  run: (sql, params) => ipcRenderer.invoke('db:run', sql, params)
}
修复建议：① 移除 webSecurity: false；② 移除通用的 db:query/get/run 暴露，改为具体的业务 API（如 photos:getAll、tags:getAll 等已有接口）；③ 在 dbAdapter 的 get/query 方法中也使用 sql.js 的 prepared statement 参数绑定，而非字符串拼接。
Critical C3. XSS 漏洞 — innerHTML 插入未转义的用户可控数据
public/index.html: 1359, 1315, 1611, 1754, 1826, 1883, 2339 等多处

前端在多处使用 innerHTML 插入标签名、文件名、错误信息等用户可控内容时未做 HTML 转义。标签内容可能包含 <img src=x onerror=alert(1)> 等 HTML 片段，会被浏览器解析执行。

// 标签名直接插入 innerHTML (第1359行)
const tagsHtml = photo.tags?.map(tag =>
  `<span class="tag-badge">${tag}</span>`  // 未转义
).join('') || '';

// showToast message 直接插入 (第1315行)
toast.innerHTML = `...<span>${message}</span>...`;  // 未转义

// 内联 onclick 拼接 (第1614行)
`<button onclick="removeBatchTag('${tag}')">`  // tag含单引号会破坏结构
修复建议：添加统一的 escapeHtml() 工具函数，对所有通过 innerHTML 插入的动态内容进行转义。或将动态内容改用 textContent 赋值，或使用 document.createElement 构建元素。
Critical C4. confirmAddTag 异步竞态条件 — 缺少 await 导致标签丢失
public/index.html:1949-1954

confirmAddTag 函数中调用 photos.updateTags() 和 exif.writeTags() 后未 await，紧接着调用 await loadPhotos() 重新加载数据。由于 IPC 调用是异步的，写入可能尚未完成就开始重新读取，导致刚添加的标签在刷新后不显示。

// 第1949-1954行 - 缺少 await
window.electronAPI?.photos.updateTags(fullPhoto.id, uniqueTags);    // 未await!
if (fullPhoto.filepath)
  window.electronAPI?.exif.writeTags(fullPhoto.filepath, uniqueTags); // 未await!
// ...
await loadPhotos(); // 此时写入可能尚未完成
修复建议：添加 await 关键字：await window.electronAPI?.photos.updateTags(...) 和 await window.electronAPI?.exif.writeTags(...)。
Critical C5. metadata.ts 完整实现但从未注册 — 死代码 + 依赖缺失
electron/ipc/metadata.ts (266行) | electron/main.ts (无导入)

metadata.ts 定义了 4 个 IPC 处理器 (metadata:writeToFile、metadata:readFromFile、metadata:batchWrite、metadata:syncFromFiles)，但 main.ts 从未调用 registerMetadataIpc()，导致这些处理器永远不会被注册。

更严重的是，该文件 import piexif from 'piexifjs'，但 piexifjs 不在 package.json 依赖中、也不在 node_modules 中。如果调用 registerMetadataIpc() 会直接崩溃。

此外，metadata.ts 与 exifTool.ts 功能高度重复——两者都实现 EXIF 评级/标签的读写，只是底层库不同 (piexifjs vs exiftool-vendored)。

修复建议：直接删除 metadata.ts。EXIF 读写已由 exifTool.ts 完整实现且功能更强大（支持 PNG/TIFF，metadata.ts 仅支持 JPEG）。

🟠 高优先级问题 (High)

影响性能或可维护性，建议尽快处理。

High H1. saveDatabase() 在每次写操作后全量序列化 — 严重性能瓶颈
electron/services/database.ts:148 | 调用方: photo.ts, tagManager.ts, album.ts 等

dbAdapter.run() 内部调用 saveDatabase()，该方法执行 db.export() 将整个数据库序列化为二进制并 writeFileSync 写入磁盘。这意味着每次 INSERT/UPDATE/DELETE 都会触发一次完整的数据库序列化+磁盘写入。

更严重的是，调用方在 dbAdapter.run() 之后又调用了一次 saveDatabase()（如 photos:updateRating、photos:toggleFavorite、albums:create 等），造成双重写入。

批量操作如 photos:updateTags（循环 INSERT 多个标签）会在循环内触发多次 saveDatabase()，每次都是全量写入。

// photo.ts - 双重保存
ipcMain.handle('photos:updateRating', (_event, id, rating) => {
  dbAdapter.run('UPDATE photos SET rating = ? WHERE id = ?', [rating, id]);
  // ↑ dbAdapter.run 内部已调用 saveDatabase()
  saveDatabase(); // ← 又调一次，双重写入
  return { success: true };
});
修复建议：① 从 dbAdapter.run() 中移除 saveDatabase() 调用；② 在批量操作完成后调用一次 saveDatabase()；③ 或改为定时自动保存（如每 5 秒检查一次 dirty flag），避免每次操作都写盘。
High H2. 启动时全量 EXIF 同步 — syncTagsToExif() 遍历所有照片
electron/main.ts:82-121, 176

应用启动时调用 syncTagsToExif()，遍历数据库中所有照片，为每张有标签的照片调用 writeExifTags()。writeExifTags 每次调用都会 new ExifTool() 并 exiftool.end()——即每张照片启动一个 Perl 子进程。对于 1000 张照片，意味着启动 1000 次 Perl 进程。

这个操作在 app.whenReady() 中以 syncTagsToExif()（无 await）异步执行，虽然不阻塞窗口创建，但会在启动后占用大量 CPU 和磁盘 IO。

修复建议：① 使用单例 ExifTool 实例（exiftool-vendored 支持复用）；② 改为增量同步——只在标签变更时同步对应照片（tagManager.ts 中已有 syncTagsToPhotoExif）；③ 移除启动时的全量同步。
High H3. 前端无虚拟滚动 — 全量 innerHTML 重建
public/index.html:1423

renderPhotoGrid() 每次执行时 photoGrid.innerHTML = '' 清空所有 DOM，然后为每张照片创建完整的 DOM 元素。没有虚拟滚动、没有分页、没有懒加载。

当照片数量达到数百张时，每次筛选/搜索/标签变更都会重建数百个 DOM 节点并重新加载所有缩略图，导致明显卡顿。删除操作中还存在双重渲染：先 renderPhotoGrid() 再 await loadPhotos()（内部再次 renderPhotoGrid()）。

修复建议：① 实现虚拟滚动（仅渲染可视区域内的 DOM，如使用 IntersectionObserver）；② 图片使用 loading="lazy" 原生懒加载；③ 删除操作后直接从 photos 数组移除元素并 renderPhotoGrid()，无需重新 loadPhotos()。
High H4. CDN 依赖 — 桌面应用离线不可用
public/index.html:8-17

Tailwind CSS、Font Awesome、jsPDF、Masonry、PhotoSwipe、Google Fonts 全部通过 CDN 引入。作为一款桌面应用（portable exe），用户在无网络环境下使用时，所有样式和图标加载失败，界面完全不可用。

其中 Masonry 和 PhotoSwipe 已引入但实际未使用，属于多余的 CDN 请求。

修复建议：① 将所有必要的 CDN 资源改为本地文件（npm install 后从 node_modules 复制到 public/vendor/）；② 在 Vite 构建中配置资源打包；③ 移除未使用的 Masonry 和 PhotoSwipe。
High H5. 单文件前端 — 2983 行无模块化
public/index.html (2983行)

所有前端代码（CSS 476 行 + HTML 740 行 + JS 1746 行）堆积在单个 HTML 文件中。所有变量和函数在全局作用域，互相耦合，无法做单元测试。变更任何小功能都需要在超大文件中搜索定位。

425 行 changelog 也硬编码在 HTML 中，每次版本更新需要修改 HTML 文件。

修复建议：利用已有的 Vite 构建工具链，将 public/index.html 拆分为标准的 Vite 项目结构：src/main.ts（入口）、src/components/（UI 组件）、src/services/（数据层）、src/styles/（样式）。可渐进式迁移，先拆分再逐步引入框架。
High H6. 硬编码本机路径 — config.ts 默认下载目录
electron/services/config.ts:55

默认下载目录硬编码为 'E:\\文档\\相册\\样片'，这是开发者本机路径。其他用户机器上该路径不存在，会尝试创建（可能因权限或盘符不存在而失败）。此路径还被用作照片删除时的回收站目录（photo.ts:143），路径不可用会导致删除功能异常。

const defaultDownloadDir = 'E:\\文档\\相册\\样片'
修复建议：使用 app.getPath('documents') 或 app.getPath('downloads') 作为默认路径，或在首次启动时引导用户选择目录。

🟡 中优先级问题 (Medium)

Medium M1. 搜索框 debounce 实现缺陷 — 多次重复渲染
public/index.html:2089

搜索框 input 事件每次触发都创建新的 setTimeout(renderPhotoGrid, 300)，但不清除前一个定时器。快速输入 10 个字符会产生 10 个定时器，全部在 300ms 后依次执行，导致 10 次全量渲染。

// 当前 (错误)
input.addEventListener('input', () => setTimeout(renderPhotoGrid, 300));

// 正确做法
let searchTimer;
input.addEventListener('input', () => {
  clearTimeout(searchTimer);
  searchTimer = setTimeout(renderPhotoGrid, 300);
});
Medium M2. resize 事件双重监听 + 无防抖
public/index.html:1514, 2558

窗口 resize 事件注册了两个监听器：一个调用 layoutMasonry()，另一个调用 renderPhotoGrid()（内部又调用 layoutMasonry()）。两个都没有防抖，拖拽窗口边框时会触发大量布局计算和 DOM 重建。

Medium M3. ExifTool 实例不复用 — 每次操作启动新进程
electron/ipc/exifTool.ts:40, 117, 152, 224

readExifData、writeExifRating、writeExifTags、writeExifData 每个函数内部都 new ExifTool() 然后调用 exiftool.end()。exiftool-vendored 设计为复用单例实例以提高性能，频繁创建/销毁会导致 Perl 子进程的启动开销。

修复建议：创建一个全局单例 let exifToolInstance: ExifTool | null = null，在首次使用时初始化，在 app 退出时 end()。
Medium M4. 错误信息拼接方式不一致 — Error 对象被 toString
public/index.html: 1658, 1688, 1986, 2244, 2323 等 9 处

多处使用 '失败: ' + e 拼接错误信息，当 e 是 Error 对象时得到 "失败: Error: message"。应使用 e.message || String(e)。

Medium M5. 项目根目录残留一次性脚本和旧发布包
photo-gallery/ 根目录

项目根目录存在 4 个一次性维护脚本（cleanup-crop.js、update-crop.js、revert-crop.js、update-batch-html.js，共 783 行）和 2 个旧版本发布包目录（portable-release-2.3/、portable-release-2.4/，各约 100MB）。此外 blackBorderCrop.ts 的功能已在 v2.0 移除但文件仍存在。

修复建议：① 删除一次性脚本或将它们移到 scripts/ 目录；② 删除旧发布包；③ 删除 blackBorderCrop.ts；④ 将 .gitignore 配置忽略 portable-release-* 和 dist-exe/。

🔵 低优先级问题 (Low)

Low L1. 两个 User-Agent 常量完全相同 — 模式切换无效
public/index.html:2668-2669

XHS_USER_AGENT 和 NORMAL_USER_AGENT 的值完全相同，"小红书模式"和"普通浏览器模式"的切换实际上没有任何效果。

截图使用 image.toPNG() 获取 PNG 数据，但文件名设为 screenshot_*.jpg，后缀与实际格式不匹配，可能导致文件管理混乱。

实现图片虚拟滚动（仅渲染可视区域 DOM）；为 resize 和搜索添加防抖；图片添加 loading="lazy"；修复双重渲染（删除后不重新 loadPhotos）。

8. ExifTool 单例化
创建全局 ExifTool 单例实例，复用 Perl 子进程。exiftool-vendored 原生支持实例复用，只需在模块顶层创建 const exiftool = new ExifTool()，在 app.on('will-quit') 时 exiftool.end()。
影响：EXIF 操作速度提升 5-10 倍
🔵 P3 — 中长期改造
9. 前端模块化拆分
将 2983 行的 index.html 拆分为标准 Vite 项目结构。可先按功能拆分为独立 JS 模块（gallery.js、lightbox.js、materialBrowser.js、settings.js），再逐步引入轻量框架（Preact 或 Vue 3）实现响应式状态管理。Changelog 从 HTML 中抽离为 JSON/Markdown 文件。
影响：代码可维护性、可测试性大幅提升，为后续功能扩展打好基础
🔵 P3 — 中长期改造
10. 考虑迁移到 better-sqlite3 或 native SQLite
当前使用 sql.js（SQLite WASM）需要手动序列化/反序列化到文件，每次写入是全量操作。迁移到 better-sqlite3（原生绑定）可获得：原生 WAL 模式（无需手动 save）、更好的并发性能、prepared statement 原生支持、无需全量序列化。
影响：数据库性能提升 10-100 倍，代码复杂度降低
